# Parshyn_nosql_3 — Граф знань для рекомендаційної системи (Neo4j + MovieLens 1M)

Фінальне завдання курсу «NoSQL та векторні бази даних». Будуємо рекомендаційний рушій
на графовій базі **Neo4j** поверх датасету **MovieLens 1M** (6 040 користувачів, 3 883 фільми,
1 000 209 оцінок): від проєктування схеми й завантаження даних до складних Cypher-запитів,
виявлення супервузлів і запуску алгоритмів **PageRank**, **Louvain**, **Dijkstra** через бібліотеку
**GDS** (Graph Data Science).

## Частина 1 — Проєктування схеми

### ASCII-діаграма графа

```
        ┌───────────────────────────────┐
        │             User              │
        │  userId   : Integer (унік.)   │
        │  gender   : "M" | "F"         │
        │  age      : Integer (код)     │
        │  occupation: Integer (код)    │
        └───────────────┬───────────────┘
                        │
                        │  :RATED { rating: Float (1..5),
                        │           timestamp: Integer (unix) }
                        ▼
        ┌───────────────────────────────┐        :HAS_GENRE      ┌──────────────────┐
        │             Movie             │ ────────────────────►  │      Genre        │
        │  movieId : Integer (унік.)    │                        │  name : String    │
        │  title   : String             │   (фільм -> 1..N        │  (унік., 18 шт.)  │
        │  year    : Integer            │    жанрів)              └──────────────────┘
        └───────────────────────────────┘
```

- **Вузли:** `User`, `Movie`, `Genre`.
- **Ребра:** `(User)-[:RATED {rating, timestamp}]->(Movie)` та `(Movie)-[:HAS_GENRE]->(Genre)`.
- **Обмеження/індекси:** `UNIQUE` на `User.userId`, `Movie.movieId`, `Genre.name` (кожне дає
  backing-індекс).

> **Коди демографії** (з README датасету). `age`: 1=«<18», 18=«18-24», 25=«25-34», 35=«35-44»,
> 45=«45-49», 50=«50-55», 56=«56+». `occupation`: 0=other, 1=academic/educator, 2=artist,
> 3=clerical/admin, 4=college/grad student, 5=customer service, 6=doctor/health care,
> 7=executive/managerial, 8=farmer, 9=homemaker, 10=K-12 student, 11=lawyer, 12=programmer,
> 13=retired, 14=sales/marketing, 15=scientist, 16=self-employed, 17=technician/engineer,
> 18=tradesman/craftsman, 19=unemployed, 20=writer. Коди зберігаємо «як є», розшифровка — тут.

### Відповіді на питання Частини 1

**1. Які сутності стали вузлами, а які — ребрами? Чому?**
Вузлами стали **самостійні сутності** зі своєю ідентичністю та атрибутами — користувачі (`User`),
фільми (`Movie`) і жанри (`Genre`). Ребрами стали **звʼязки/дії між сутностями**: факт оцінювання
(`:RATED`) та належність фільму до жанру (`:HAS_GENRE`). Правило просте: те, про що ми хочемо
зберігати дані й що бере участь у багатьох звʼязках, — вузол; те, що *поєднує* дві сутності, — ребро.
Графова модель тут природно лягає на предметну область: «користувач оцінив фільм», «фільм належить
жанру» читаються як речення.

**2. Оцінка — це ребро `(User)-[:RATED]->(Movie)` чи окремий вузол `(Rating)`? Trade-off.**
Ми обрали **ребро `:RATED`** з властивостями `rating` і `timestamp`. Аргументи:
- *Чому ребро.* Оцінка не має власної ідентичності поза парою (користувач, фільм) і не має власних
  звʼязків. Ребро економніше за памʼяттю (немає зайвого вузла + двох ребер замість одного) і робить
  обходи типу «користувач → фільм → інший користувач» (основа колаборативної фільтрації) **на крок
  коротшими й швидшими**. 1M ребер проти 1M зайвих вузлів — це суттєво.
- *Коли був би доречний вузол `Rating`.* Якби оцінка мала **власні звʼязки чи багату структуру**:
  коментарі до оцінки, теги, «лайки» інших користувачів на цю оцінку, історію змін рейтингу в часі,
  модерацію тощо. Вузол `Rating` — це фактично реіфікація звʼязку; вона виправдана, коли звʼязок сам
  стає обʼєктом, на який щось посилається. У нашому датасеті цього немає → ребро оптимальне.

**3. Чому жанри — окремі вузли `(Genre)`, а не список у властивості `Movie.genres`?**
- **Запити «спільного жанру» стають обходом**, а не скануванням масивів: `(:Genre {name:'Thriller'})
  <-[:HAS_GENRE]-(m)` миттєво дає всі трилери через індекс на `Genre.name`. Якби жанри лежали списком
  у властивості, довелося б сканувати **всі** фільми й перевіряти входження в масив.
- **Агрегації по жанрах** (середній рейтинг жанру, к-сть оцінок) пишуться природно через `HAS_GENRE`.
- **Нормалізація:** назва жанру зберігається один раз (18 вузлів), а не дублюється у тисячах рядків;
  легко додати атрибути жанру або звʼязки жанр-жанр.
- Платою є поява **супервузлів** (Genre — хаби, див. Частину 4), але вигода для запитів переважає.

## Частина 2 — Завантаження даних

Код: [`queries/part2_load.cypher`](queries/part2_load.cypher). Повний лог:
[`queries/results/part2_load.out`](queries/results/part2_load.out).

**Пояснення кроків:**

1. **Індекси/обмеження ДО ребер.** `CREATE CONSTRAINT ... IS UNIQUE` на `User.userId`,
   `Movie.movieId`, `Genre.name`. Кожен constraint автоматично створює backing-індекс. Це
   **критично**: під час завантаження ~1M ребер кожен рядок робить `MATCH` по `userId`/`movieId`;
   без індексу це був би повний скан вузлів на *кожен* рядок (години). З індексом — секунди.
2. **Вузли через `MERGE`** (а не `CREATE`): захист від дублів при повторному запуску скрипту
   (ідемпотентність). CSV-значення приходять рядками, тому числові поля приводимо: `toInteger(...)`.
3. **Рік фільму** витягуємо з назви формату `"Title (YYYY)"`:
   `toInteger(substring(row.title, size(row.title)-5, 4))`.
4. **Жанри:** `split(row.genres, '|')` → `MERGE (g:Genre)` + `MERGE (m)-[:HAS_GENRE]->(g)`.
5. **Ребра `:RATED` через `apoc.periodic.iterate`.** ~1M ребер не можна вантажити однією
   транзакцією — впаде через памʼять/таймаут. APOC розбиває на батчі по 10 000.
   **`parallel: false`** — бо кілька потоків конкурували б за блокування одних і тих самих вузлів
   `User`/`Movie` (ми робимо `MERGE` ребра). Паралелізм безпечний лише якщо вузли точно створені й у
   тілі лише `MATCH` — тут краще не ризикувати.

**Результат завантаження** (звірка лічильників — усе збіглося, завантаження зайняло ≈19 с):

| Сутність | Очікувано | Отримано |
|----------|-----------|----------|
| `User`   | 6 040     | **6 040** ✅ |
| `Movie`  | 3 883     | **3 883** ✅ |
| `:RATED` | 1 000 209 | **1 000 209** ✅ |
| `Genre`  | 18        | **18** ✅ |

```

101, 1000209, {}        // 101 батч, 0 помилок
```

### Відповіді на питання Частини 3 (семантика довжини шляху)

Граф **дводольний**: ребра `:RATED` ведуть лише `User → Movie`. Тому будь-який шлях «користувач →
... → користувач» має **парну** довжину, чергуючи `User` і `Movie`.

1. **Що означає довжина шляху?** К-сть ребер `:RATED` між двома користувачами. Це міра «соціальної»
   близькості за спільними переглядами.
2. **Довжина 2** = два користувачі оцінили **один і той самий фільм** (один спільний фільм-міст).
   Найтісніший можливий звʼязок.
3. **Довжина 4** = звʼязок через **одного проміжного користувача**: `U1 → M_a ← U_x → M_b ← U2`
   (U1 і U2 не мають спільного фільму, але обидва мають спільний фільм із третім користувачем U_x).
   **Довжина 6** = через **двох проміжних користувачів** — ще слабша, опосередкована схожість.

### Відповіді на питання Частини 4

**1. Які вузли — супервузли і скільки в них звʼязків?**
Є **два типи** супервузлів:
- *За абсолютним degree* лідирують **блокбастери** — `American Beauty` (3 430 звʼязків ≈ 3 428
  оцінок + жанри), трилогія `Star Wars` (~2 900–3 000), `Jurassic Park` (2 675) — та **найактивніші
  користувачі** (user 4169 — 2 314 оцінок).
- *Архітектурні* супервузли — **жанрові вузли**: їх лише **18**, але `Drama` звʼязаний з **1 603**
  фільмами, `Comedy` — з **1 200**. Це класичні «вузькі горловини» графа.

**2. Чому запит через супервузол повільніший навіть з тими ж індексами?**
Індекс прискорює **пошук стартового вузла**, але не обхід його ребер. Коли запит «заходить» у
супервузол, планувальник мусить **розгорнути всі його інцидентні ребра** — для `Drama` це 1 603
фільми, для `American Beauty` — 3 430 користувачів. Якщо далі йде ще один крок (наприклад, «інші
фільми тих самих користувачів»), кількість шляхів **множиться** і дає комбінаторний вибух: робота
росте не з розміром відповіді, а зі ступенем супервузла. Індекс тут не допомагає — він про *пошук*,
а не про *expand*.

**3. Яку стратегію застосувати для цього датасету (а жанри — теж супервузли?)?**
Так, жанри — найнебезпечніші супервузли (мало вузлів, величезний degree, тож запити природно
маршрутизуються крізь них). Стратегії:
- **Не використовувати `Genre` як півот** у «гарячому» шляху. Запит «фільми того ж жанру, що X»
  через `Drama` торкнеться 1 603 фільмів. Краще спершу звузити селективними фільтрами
  (конкретні користувачі/фільми/пороги рейтингу), і лише потім розгортати.
- **Якорити обхід на низько-degree боці** — починати з селективного вузла (конкретний користувач),
  а не з хаба, щоб планувальник стартував із малого набору.
- **`LIMIT` і пороги** (напр. `weight >= 10` при матеріалізації, як у Частині 5) — відсікають
  «шумові» звʼязки до розгортання.
- **Денормалізація**: тримати на вузлах попередньо обчислені агрегати (avgRating, к-сть), щоб не
  ходити крізь хаб заради лічильника (див. покращення схеми в Частині 6).

## Частина 5 — Графові алгоритми (GDS)

Код: [`queries/part5_gds.cypher`](queries/part5_gds.cypher). GDS не працює зі збереженим графом
напряму — спершу матеріалізуємо допоміжні ребра й створюємо **проєкцію в памʼяті**.

### 5.1 PageRank на графі фільмів
Будуємо граф `movieGraph`, де фільми звʼязані ребром `CO_RATED`, якщо їх обидва високо оцінили (≥4)
ті самі користувачі (`weight` = к-сть таких користувачів; беремо пари з `weight ≥ 10`, топ-50 000).
Проєкція: **3 883 вузли, 100 000 ребер** (UNDIRECTED). Результат PageRank:

```
movie, pageRank
"American Beauty (1999)", 9.6596
"Star Wars: Episode IV - A New Hope (1977)", 9.136
"Star Wars: Episode V - The Empire Strikes Back (1980)", 9.0977
"Raiders of the Lost Ark (1981)", 7.9382
"Fargo (1996)", 7.0343
"Silence of the Lambs, The (1991)", 6.7605
"Godfather, The (1972)", 6.3352
"Matrix, The (1999)", 6.2873
"Shawshank Redemption, The (1994)", 6.2778
"Sixth Sense, The (1999)", 6.2444
```

**Питання: що означає високий PageRank — просто «популярний фільм» чи щось інше?**
Це **не лише популярність**. PageRank вимірює **центральність у мережі спільних смаків**: фільм має
високий ранг, якщо його високо оцінюють ті самі люди, що й *інші впливові, добре оцінені* фільми.
Показовий приклад — **`Godfather`**: за кількістю оцінок він *не* входить у топ (його немає серед
найбільш-оцінюваних із Частини 4), але за PageRank він **7-й**, бо сидить у щільному ядрі «фільмів,
які цінують поціновувачі хорошого кіно». Тобто PageRank винагороджує фільм за **якість компанії**, у
якій він перебуває, а не лише за обсяг оцінок. Це робить його кращим за «к-сть оцінок» сигналом для
рекомендацій: він підіймає фільми-«мости» між кластерами якісного кіно.

### 5.2 Виявлення спільнот (Louvain)
Граф `userSimilarity`: користувачі звʼязані ребром `SIMILAR`, якщо обидва поставили **«5»** спільним
фільмам (`weight` = к-сть; `weight ≥ 5`, топ-50 000 ребер). Поріг саме «=5» (а не «≥4») тримає
к-сть user-user пар керованою на повному 1M (інакше популярні фільми дають мільйони пар і ризик OOM).

10 найбільших спільнот і `modularity`:
```
communityId, size            communityCount, modularity, ranLevels
4276, 837                     4574, 0.1674, 1
5681, 305
2063, 248
3390, 80
(далі — переважно одиночні вузли: користувачі без ребер SIMILAR)
```
Топ-3 жанри найбільших спільнот (за високо-оціненими фільмами):
```
communityId, size, top3Genres
4168, 855, ["Drama", "Comedy", "Action"]
4032, 318, ["Comedy", "Drama", "Action"]
2029, 297, ["Drama", "Comedy", "Thriller"]
```
> *Примітка:* Louvain — евристика, тож `communityId` і розміри трохи різняться між запусками
> (837↔855 тощо); `modularity ≈ 0.167`. Невисока modularity пояснюється тим, що граф складається з
> кількох щільних кластерів **плюс** маси одиночних вузлів (користувачі, чиї ребра не потрапили у
> топ-50 000), які «розмивають» метрику.

**Питання 1: чи відповідають кластери інтуїтивним групам («любителі бойовиків», «арт-хаус»)?**
Лише **частково**. Топ-3 жанри всіх великих спільнот — `Drama/Comedy/Action`, тобто домінують
**мегажанри** (вони ж найчисленніші: Drama=1603, Comedy=1200 фільмів). Тому на рівні «сирих» топ-жанрів
кластери виглядають схожими — це радше групи за **інтенсивністю активності**, ніж за нішевим смаком.
Щоб побачити справжні відмінності («бойовики» vs «арт-хаус»), треба **нормувати** частку жанру в
спільноті на його базову частку в усьому датасеті (lift), а не дивитися на абсолютні лічильники.
**Питання 2: як перевірили?** Для 5 найбільших спільнот вивели топ-3 жанри по фільмах, які її
учасники оцінили ≥4 (запит у `part5_gds.cypher`, крок 3c). Саме звідси видно домінування мегажанрів.

### 5.3 Найкоротший шлях між користувачами (Dijkstra)
Та сама проєкція `userSimilarity`. **Важливий нюанс:** Dijkstra **мінімізує суму ваг**, а наш
`weight` = к-сть спільних фільмів (**більше = схожіші**). Тож «сирий» Dijkstra трактує сильні звʼязки
як **дорожчі** й уникає їх. Це видно емпірично:

```
src,  dst,  totalCost, hops, chain
4277, 4169, 64.0,      2,    [4277, 5952, 4169]   // хоча 4277 і 4169 ЗВʼЯЗАНІ напряму!
4277, 5795, 64.0,      2,    [4277, 5786, 5795]
4277, 1285, 64.0,      2,    [4277, 5512, 1285]
4277, 27,   98.0,      3,    [4277, 5952, 4169, 27]
```
Тобто між двома хабами Dijkstra обирає **обхід у 2 хопи** через слабкі ребра (сумарна вага 64),
бо пряме ребро має «дорогу» вагу >100. Для семантично коректного «найсхожішого шляху» треба
інвертувати вартість (`cost = 1.0/weight`) — варіант наведено у `part5_gds.cypher` (5.3, блок B).

**Справжня** відстань (незважений найкоротший шлях по `SIMILAR`):
```
src,  dst,  unweightedHops
4277, 4169, 1        4277, 1285, 1
4277, 5795, 1        4277, 549,  1
1285, 3539, 1        5795, 3539, 1
```

**Питання 1: наскільки «тісний світ»?** Надзвичайно тісний. Ядро активних користувачів — фактично
**кліка**: між усіма великими хабами незважена відстань = **1** (прямий звʼязок), периферійні
користувачі дістаються ядра за 2–3 хопи.
**Питання 2: середня довжина шляху? Гіпотеза «шести рукостискань»?** У межах звʼязної компоненти
середня відстань ≈ **1–2** хопи. Гіпотеза шести рукостискань **багаторазово перевиконується**: тут
це радше «один-два потиски руки». Причина — спільні популярні фільми (American Beauty, Star Wars)
оцінили тисячі користувачів, тож майже будь-яка пара активних користувачів має спільний фільм або
спільного «сусіда». Зворотний бік: користувачі без сильних `SIMILAR`-ребер опиняються в окремих
компонентах (для них шляху немає — у незваженому запиті позначено `-1`).

## Частина 6 — Аналіз і висновки

**1. Граф vs SQL. Які запити Частини 3 складно/неможливо написати в SQL?**

Найпоказовіший — **Запит 6 (найкоротший ланцюжок між користувачами)**. У графі це один рядок:
`MATCH p = shortestPath((u1)-[:RATED*..6]-(u2))`. У SQL прямого аналога немає — потрібен
**рекурсивний CTE**, що крок за кроком будує ребра «користувач–спільний фільм–користувач»:

```sql
WITH RECURSIVE
bridge AS (                                   -- ребро user-user через спільний фільм
  SELECT a.user_id AS u1, b.user_id AS u2
  FROM ratings a JOIN ratings b
    ON a.movie_id = b.movie_id AND a.user_id < b.user_id
),
paths AS (
  SELECT u1 AS start, u2 AS node, 1 AS depth, ARRAY[u1, u2] AS path
  FROM bridge WHERE u1 = 1
  UNION ALL
  SELECT p.start, br.u2, p.depth + 1, p.path || br.u2
  FROM paths p JOIN bridge br ON br.u1 = p.node
  WHERE p.depth < 6 AND NOT (br.u2 = ANY(p.path))
)
SELECT * FROM paths WHERE node = 6040 ORDER BY depth LIMIT 1;
```
Проблема не лише в багатослівності: проміжна таблиця `bridge` — це **всі пари користувачів, що мають
спільний фільм**. Через популярні фільми (тисячі глядачів кожен) це **мільярди** рядків — той самий
«вибух», який ми бачили в Частині 5. SQL мусить (концептуально) матеріалізувати ці пари, тоді як
Neo4j обходить граф **ліниво**, розгортаючи лише потрібні ребра від двох кінців, поки не зустрінеться.
Тому запит 6 у SQL технічно можливий, але **практично неробочий** на 1M; у графі — тривіальний.
Запит 5 (рекомендація) у SQL писати теж незручно (кілька self-join-ів і підзапитів замість одного
читабельного шаблону), хоча він і виконуваний.

**2. Де граф програє? Для яких задач краща реляційна модель?**
- **Масові агрегації по всьому датасету** — «середній рейтинг по кожному з 18 жанрів за всю історію»,
  «розподіл оцінок по місяцях», «топ-100 фільмів за к-стю оцінок». Це повні сканування + `GROUP BY`,
  у чому колонкові/реляційні рушії з індексами та векторизацією **швидші**, ніж обхід графа.
- **Звіти й аналітика (OLAP)** — багатовимірні зрізи, `ROLLUP`/`CUBE`, віконні функції над великими
  обсягами. SQL зрілий і оптимізований саме під це.
- **Експорт/ETL і строгі схеми** — вивантаження мільйонів рядків у плоскі таблиці, обмеження
  цілісності, транзакційні масові оновлення. Реляційна модель тут зручніша й передбачуваніша.
- Загальне правило: граф виграє на **глибоких/змінної довжини обходах звʼязків** (рекомендації,
  шляхи, спільноти), реляційна БД — на **наборово-орієнтованих агрегаціях і звітності**.

**3. Покращення схеми, які прискорили б конкретні запити Частини 3.**
- **Денормалізувати агрегати оцінок на вузол `Movie`** — `Movie.avgRating` і `Movie.numRatings`,
  оновлювані при завантаженні/періодично. Прискорює **Запит 1** (Thriller із avg>4): замість обходу
  всіх ребер `:RATED` кожного фільму — читання двох властивостей + фільтр; з індексом на `avgRating`
  можна одразу брати фільми з рейтингом > 4. Аналогічно агрегат на `Genre` пришвидшив би **Запит 4**.
- **Окреме ребро/мітка для високих оцінок** — напр. `(:User)-[:LIKED]->(:Movie)` (матеріалізація
  `rating ≥ 4`) або індекс на властивості ребра `RATED.rating`. Це різко прискорює **Запит 5**
  (рекомендації) і всі алгоритми Частини 5, бо вони щоразу фільтрують `rating ≥ 4`/`= 5`: замість
  перевірки властивості на кожному ребрі обхід одразу йде лише по «лайках». Платою є додаткова памʼять
  і підтримка консистентності при оновленні оцінок.
